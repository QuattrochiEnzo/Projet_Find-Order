La note finale du projet inclut à la fois, une partie concernant la méthode 
utilisée et les résultats obtenus, et une partie concernant la qualité de 
l'implémentation informatique mise en oeuvre. Pour que vous puissiez mettre 
votre code en forme pour le livrable final, je vous fournis la liste des 
critères que je vais utiliser pour noter la partie implémentation.

Le principe général est qu'il s'agit d'un projet "professionnel" et par 
conséquent, j'attends un code qui soit le plus professionnel possible, ce qui 
peut se décliner selon trois critères principaux : lisibilité, extensibilité, 
documentation.

* Lisibilité

En génie logiciel, on considère qu'un code lisible est celui qu'un développeur
expert est capable de comprendre à plus de 95% en une seule lecture. Ce n'est
pas un objectif très difficile à atteindre si l'on respecte les conventions
usuelles qu'on a largement eu l'occasion d'aborder l'an dernier en "outinfo" :

- Utilisation d'identificateurs explicitant sans ambiguité, le rôle de chacun 
des modules, classes, fonctions, méthodes, variables, attributs, paramètres...

- Utilisation systématique des docstrings ou annotations (selon les conventions
standards du langage de programmation utilisé) à tous les niveaux de votre code
(paquetages, modules, classes, méthodes, fonctions)

- Et bien évidemment, je rappelle que l'ensemble des identificateurs, des
docstrings et des commentaires devront être en anglais (même si dans le code
fourni par le client, il y a un mélange français/anglais assez aléatoire)

- Comme je vous l'ai expliqué l'an dernier, après avoir expérimenté à peu près
tout ce qui existe en matière de mise en oeuvre des commentaires, je suis devenu
un partisan inconditionnel du "Storytelling Coding" qui fournit, de très loin,
la meilleure valeur ajoutée en lisibilité gagnée par rapport au temps passé à
écrire les commentaires. D'autant plus que, lorsqu'elle est bien drivée, l'IAG
est vraiment excellente pour rajouter ce type de commentaires à votre place 

- Pour la mise en oeuvre précise du storytelling, je vous invite à reprendre 
les différents exemples que j'ai fournis en "outinfo" : l'idée de base est 
d'organiser les lignes de code sur 120 chars max avec à gauche la partie code 
(80 chars max), et à droite la partie commentaire (placée sur l'espace non 
utilisé, mais en restant toujours inférieur à 120 chars au total). Le principe 
du storytelling consiste à écrire juste la bonne dose et le bon niveau 
d'abstraction pour ces commentaires, pour permettre au lecteur de comprendre 
l'enchainement des opérations effectuées par la fonction, sans être obligé de 
lire la partie code de chaque ligne. A la limite, un lecteur qui ne maîtrise 
pas du tout le langage de programmation utilisé dans le code, doit être capable
de comprendre les traitements effectués par chacune des lignes. L'avantage de
l'anglais est qu'il permet des commentaires extrêment compacts, typiquement
tous les commentaires seront de la forme "verbe d'action + complément", en
supprimant au maximum les mots qui n'apportent rien à la compréhension de
l'action réalisée (par exemple, pas de déterminants, pas d'adjectifs, etc)

- Les commentaires sur plusieurs lignes (donc hors storytelling) sont réservés
pour la description d'algorithmes ou de structures de données particulièrement
complexes. Ils se placent généralement soit en début de fonction (derrière la
docstring de la fonction), soit en début de module (derrière la docstring du
module)

- L'architecture du code participe très fortement à sa lisibilité : plus un 
code est gros, plus il doit être organisé selon une structure hiérarchique très 
stricte, avec des noms de modules et des noms de packages qui permettent de 
savoir exactement où chercher, lorsqu'on veut trouver une fonctionnalité 
précise. Dans votre cas, vous allez être sur une taille de code intermédiaire 
(un millier de lignes, grand maximum) donc mettre tout le code dans un seul 
dossier, divisé en une demi-douzaine de modules est, a priori, une architecture 
adéquate. Mais on peut envisager de rajouter un niveau de hiérarchie, en créant 
par exemple, un package pour tout ce qui est lecture/écriture de fichiers, un 
second package pour le noyau de calcul et un dernier package pour la partie 
visualisation graphique des solutions. Les deux architectures sont parfaitement
défendables, à vous de voir celle qui est le mieux adapté à votre code

- La compacité du code est un élément fondamental de la lisibilité : lire un 
code trop verbeux et pas assez dense oblige à d'incessants scrollings en avant 
et en arrière dans la fenêtre de l'IDE, et sollicite la mémoire de travail de 
manière extrêmement lourde, ce qui fait survenir très rapidement une fatigue 
cognitive. A l'inverse, un code compact, à condition qu'il soit bien épaulé par 
du storytelling, permet d'utiliser des techniques de lecture rapide pour mettre 
en oeuvre une acquisition à haut niveau des fonctionnalités implémentées dans 
le code. Par défaut, le code créé par une IAG est presque l'exact contraire de 
ce qu'on attend en matière de compacité et de lisibilité. Il vous faudra donc 
donner des instructions très précises pour expliquer ce que vous voulez 
exactement concernant la forme du code à générer, sauf évidemment si vous 
adorez le fait de devoir réécrire tout le code fourni par l'IAG.

- Comme je l'avais mentionné l'an dernier en "outinfo", un développeur avancé 
en Python arrive en moyenne, à mettre en une ligne de code ce qui nécessiterait 
entre 10 et 25 lignes de code C ou C++, donc la propriété "code compact et 
lisible" est beaucoup plus facile à obtenir en Python qu'en C/C++. La (très 
bonne) règle classique "jamais plus de 20 lignes par fonction", implique qu'un 
code C/C++ va donc contenir beaucoup plus de fonctions qu'un code Python. Mais 
n'oubliez pas, la (très mauvaise) règle "une instruction = une ligne de code" 
est le genre de chose qui étaient préconisés par les développeurs des années 
1970-1980 (et malheureusement aussi par certains de vos enseignants en 2025).
Le point virgule existe pour séparer des instructions sur une même ligne, alors 
utilisez-le ! D'autant plus dans le cas où ces instructions forment un groupe 
homogène qui pourra être commenté par une même phrase de storytelling. On 
pourrait même carrément aller à l'extrême : la granularité des lignes de code 
est isomorphe à la granularité des phrases du storytelling

- Dernière chose importante : il est INDISPENSABLE que votre code final ne 
permette pas de détecter qu'il y a eu plusieurs développeurs. Il faut vous 
mettre d'accord dès le début du projet sur un "coding style" ultra précis (sur 
les choix et la graphie des identificateurs, sur les indentations de blocs, sur 
les espaces entre opérateurs, sur la forme des docstrings et des commentaires, 
etc, etc, etc). Si vous faites ce travail dès le départ, cela vous permettra de 
créer des règles très précises à donner à l'IAG, pour obtenir d'elle un code 
quasiment définitif avec un processsus one-shot

* Evolutibilité

Là encore, le principe général est simple : aucun élément spécifique du problème
à résoudre ne doit figurer "en dur" dans le code source, pour permettre une
évolution rapide aussi bien des algorithmes que des structures de données. Dans
l'idéal, un refactoring complet du code ne devrait pas prendre plus de 1H par
bloc d'une centaine de lignes. Comme vu en cours l'an dernier, cela s'obtient en
combinant trois catégories de bonnes pratiques :

- Utilisation préférentielle de structures de données génériques choisies parmi 
les conteneurs classiques fournis par le langage. Globalement, le développement 
d'une structure spécifique au problème à résoudre, est judicieux uniquement 
lorsque cela permet d'obtenir un bénéfice important sur les performances. Mais 
évidemment en pratique, il est très rare que l'on dispose de cette info avant
d'avoir une première version fonctionnelle, donc le choix de développer ou pas
une structure spécifique pour certains aspects du problème à résoudre, se prend
généralement au premier ou au second refactoring pour le module considéré

- Utilisation de fichiers de configuration pour stocker aussi bien les données 
du problème à résoudre (pour vous, c'est déjà fait avec les fichiers fournis 
par le client qui sont sous la forme de fichiers texte semi-structurés) mais 
également les paramètres qui vont contrôler votre solveur. Il est évidemment 
préférable de piocher parmi les formats standards en fonction du type de 
données à stocker (toml, csv, json, xml...) afin de ne pas avoir à  réécrire 
les parsers associés. Attention, même les éventuelles bornes supérieures et 
inférieures sur les valeurs de ces paramètres, devraient se trouver clairement 
identifiées dans ces fichiers de configuration. Le principe général est de 
sortir le maximum de constantes de votre code pour les inclure dans des 
fichiers de configuration, ce qui permettra de modifier la configuration du 
solveur sans être obligé d'éditer le code

- Utilisation d'un paradigme de programmation adapté à la complexité du projet. 
En clair, pour un script de quelques dizaines de lignes destiné uniquement à 
réaliser des actions simples (e.g. conversions de formats de données), le 
paradigme "procédural" est parfaitement adapté. Par contre, lorsque la 
complexité des traitements à effectuer augmente, les principes généraux du 
paradigme "objet" (encapsulation, dérivation, surcharge de méthodes) 
fournissent des outils naturels pour améliorer l'extensibilité d'un code. Dans 
le cas de votre projet, vous allez vraisemblablement vous retrouver dans la 
zone de transition où l'un ou l'autre des paradigmes peut se justifier. Il n'y
aura donc, ni bénéfice ni pénalité à utiliser du procédural ou de l'objet. Par
contre, mélanger des paradigmes différents est généralement considéré comme une
très mauvaise idée, sauf si le code est clairement divisé en plusieurs entités
distinctes et autonomes qui ne communiquent pas directement (typiquement les
maillons d'une chaîne de traitements, où chacun ne communique avec ses voisins
qu'à travers des fichiers de données en entrée ou en sortie)

- De la même manière, le choix entre des modules 'classiques' ou un 'notebook' 
pour la structure du code s'effectue habituellement assez en amont du projet.
Dans votre cas, on se trouve avec un projet "old-school" qui va essentiellement 
s'exécuter sous forme d'une boîte noire : en entrée, on dispose de fichiers de 
données décrivant l'instance, et en sortie, on fournit d'autres fichiers de 
données décrivant la solution, tout cela avec très peu d'interactions ni de 
visualisations intermédiaires. Dans ce type de projet, le concept de notebook 
n'apporte pas vraiment de plus-value sur la version finale du code, même si 
pendant la phase développement, l'interactivité d'un développement par cellules 
permet de gagner (beaucoup) de temps lorsqu'on a les bons réflexes.

* Documentation

Les outils de documentation automatique, par extraction des annotations de 
code, sont devenus incontournables dans le développement logiciel professionnel,
notamment pour guider le développeur lors de sa navigation dans l'arborescence
(parfois très complexe) de paquetages et de modules. Suivant les langages de
programmation, il existe des standards de facto: par exemple, Doxygen pour du
code C/C++/Java et Sphinx pour du code Python et d'autres langages. En plus de
l'extraction automatique, chacun de ces outils permet de personnaliser et
hiérarchiser la documentation produite. Certains sites comme "readthedocs.org"
se sont même spécialisés dans le stockage gratuit et la création collaborative
de documentation, basée sur Sphinx.

Lorsque le code complet ne fait que quelques centaines de lignes (ce qui sera 
vraisemblablement le cas pour votre projet), ce type d'outil n'est généralement 
pas indispensable, car dans ce cas de figure, la lecture intégrale d'un code 
commenté est la meilleure option pour en comprendre la structure et le 
fonctionnement. Par conséquent, dans le cadre de ce projet, la mise en oeuvre 
des outils de documentation automatique n'est pas demandé explicitement. Mais 
évidemment, les groupes qui souhaitent se lancer, et fournir avec leur 
livrable, une doc au format Sphinx ou Doxygen bénéficieront d'un bonus dans 
leur note finale, car c'est un processus qu'il n'est pas inutile d'avoir testé 
au moins une fois durant sa formation.
